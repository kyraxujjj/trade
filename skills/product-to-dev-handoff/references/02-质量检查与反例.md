# 研发交付质量检查

## 一次交付前的八轮走查

1. **业务走查**：从首次进入到获得结果，再走一次返回和重复进入；每步是否有出口。
2. **状态走查**：同一个“成功/完成”在全文是否只有同一种业务含义；独立维度是否被误用。
3. **字段走查**：显示字段是否有来源，提交字段是否有校验；默认值缺失或无效是否有处理。
4. **角色走查**：不同角色、其他资源作用域、关系已变化的用户是否会获得错误能力。
5. **异步走查**：延迟、超时、重试、外部回执缺失是否可能造成重复或虚假成功。
6. **关系走查**：ID 是否带来源，是否把姓名当唯一键，删除/解绑是否超出目标范围。
7. **验收走查**：每条核心规则是否能在用例中判定对错；示例数据是否被误当业务规则。
8. **就绪走查**：未决项在正文中是否仍被写成确定规则；是否对尚未验证的系统能力作了承诺。

## 常见产品语言如何补成研发可以实现的表达

| 原始表达 | 缺口 | 应补成的规则 |
| --- | --- | --- |
| 自动带出内容 | 来源、时机、编辑范围 | 从所选源对象读取，在表单首次初始化时带入；后续仅编辑任务副本；重新进入是否恢复草稿另列 |
| 只允许一个 | 一个什么、在哪个范围 | 定义资源作用域、业务唯一键、有效状态、并发裁决与删除后的重新创建 |
| 发布后同步 | 同步给谁、何时、凭什么 | 服务端保存权威结果；操作成功及列表恢复时重取；如需实时，再定义推送/轮询能力 |
| 显示未完成 | 谁未完成、完成什么 | 定义成员范围与完成标准；缺失、加载失败不视为零 |
| 复用原页面 | 哪些沿用、哪些变更 | 引用组件及约定，逐项列差异；未见代码时不宣称接口已确认 |
| 支持提醒 | 提醒谁、何时、什么状态 | 定义接收对象、调度时区、授权、去重、执行前校验、删除/修改的影响 |
| 分享后完成 | 平台是否给可靠证据 | 区分发起、确认、取消、未知；核实平台能力，再决定能显示什么完成状态 |
| 名单匹配异常 | 异常种类与恢复 | 明确未找到、多个候选、关系冲突、来源失败；分别提供核对或重试动作 |
| 可以删除 | 删除什么、谁能删 | 定义权限与记录状态，并处理计数、历史链接、定时任务、唯一键及再次创建 |
| 不限制每天学多少 | 不只是一处按钮 | 移除业务状态与配额限制，补齐继续/重练入口，区分本轮和累计记录，并兼容旧已结束缓存 |

## 禁止的推断

- 有一个绿色对勾，就断言后端已完成写入。
- 给所有失败都加“重试”按钮，却不检查该操作是否可重复执行。
- 平台有分享入口，就断言能回调“已送达指定群”。
- 截图上没有错误态，就认为无需设计错误恢复。
- 复用旧页面，就默认旧权限、字段、上传限制与本次一致。
- 用户没有提供接口，就编造一个已存在的 REST 路径和数据库表名。
- “未完成人数未知”被转换成零，进而显示全部完成。
- 把两个来源系统中数值一样的 ID 当作同一个实体。
- 用同一个账号、同一姓名、同一班级三个条件中的任意一个，替代明确的学生关系验证。
- 文档仍有关键 P0，却宣称所有内容均可直接上线开发。

## 成熟度自检

以下任一项未解决，受影响部分应保留为“可评审”，不能宣称已可开发：

- 核心对象或唯一性范围存在两套互相冲突的定义。
- 不清楚谁拥有数据、谁可以操作。
- 成功状态依赖尚未确认的平台回执。
- 跨系统关联存在多个候选，未确定如何确认正确对象。
- 关键时间冲突没有处理策略。
- 用户可以走进页面，却没有合法返回或恢复路径。

不要为了消灭待决项而假装知道答案。给出具体建议、影响范围、需要的决定或证据，才是对研发有用的交付。

## 写完之后的压缩

删掉没有业务后果的术语堆砌。相同字段和组件只定义一次，其他位置引用编号。只保留与本次功能相关的状态、依赖和异常，不强行扩成企业级通用平台。
