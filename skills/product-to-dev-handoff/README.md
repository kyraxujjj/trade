# 产品需求到研发规格 Skill

用途：以后只提供想做的功能、页面内容或截图，让 AI 输出结构明确、能评审、能估工、能编写实现与验收任务的中文功能规格。

这是可复制使用的 Skill 源文件包，通过现有 GitHub 仓库提供下载。它没有修改现有 App，也不会自动安装插件或注册技能；请按下面的方式使用。

## 包内文件

- `SKILL.md`：主 Skill，定义输入理解、事实/建议分级、推导流程和输出门槛。
- `references/01-原型拆解与复用逻辑.md`：本次原型的 16 套可复用思路，逐条给出原型依据、抽象方法、交付要求和反例。
- `references/02-质量检查与反例.md`：交付前走查和常见“产品语言 → 研发语义”转换。
- `templates/研发功能规格模板.md`：通用研发交付文档结构。
- `templates/原型旁注模板.md`：按页面输出可直接贴到原型旁的规则文字。
- `examples/督促学习-研发规格示例.md`：把本次两张原型整理成的完整实例，明确保留 P0 未决点。
- `examples/督促学习-原型旁注稿.md`：与完整规格配套的旁注视图，适合直接放在原型黄色说明区。
- `examples/最少输入-学习复习.md`：用一段新需求演示如何自动补流程、状态和验收，而不硬套班级/分享逻辑。
- `examples/轻量功能-收藏.md`：展示简单需求如何压缩交付，不机械添加复杂平台设计。
- `校验说明.md`：本包完成过的结构检查、规则追踪走查及验证边界。

## 在 Codex 中使用

把整个 `product-to-dev-handoff` 文件夹放到项目的：

```text
<项目目录>/.agents/skills/product-to-dev-handoff/
```

保留 `SKILL.md`、`references/`、`templates/` 和 `examples/` 的相对位置。在支持该目录发现机制的 Codex 会话中重新打开项目或刷新技能发现，再调用：

```text
使用 $product-to-dev-handoff。
我要做的功能：……
目标用户：……（知道就填）
页面需要展示：……
关键操作与想达到的结果：……
现有系统/可复用能力：……（没有资料就注明未知）
硬性要求：……
请直接输出研发功能规格，补齐必要的衔接、状态、数据和验收。
先给按页面分组、可贴在原型旁的说明，再附必要的研发细节。
把不确定的规则单独标为建议或待决，不要假装现有接口已经存在。
```

不要求每次填写全部项目。只给功能和内容也能先产出规格草案；真正影响核心结果的缺口会集中标出，而不是用猜测填平。

没有自动识别到该 Skill 时，可以明确让助手读取这个文件夹中的 `SKILL.md`，然后按其引用读取相关模板。

## 在普通聊天或其他 AI 工具中使用

使用包外随附的 `product-to-dev-handoff-单文件版.md`，它合并了主规则、通用模板和质量检查。上传该文件或把它作为项目指令，再提供需求。完整原型拆解和实例可按需附上，不必每次塞入所有案例。

本包不宣称已注册到任何平台的技能市场，也不依赖特定模型、SDK 或第三方插件。

## 推荐的首次用法

```text
使用这个 Skill，按附件截图分析并输出研发交付文档。
优先生成原型旁注版，再附必要的完整规格。
先还原业务闭环，再给页面、字段、状态、数据契约与验收。
重点检查：我的表述是否省略了前置条件、成功依据、返回路径和异常恢复。
常规细节请给建议；核心规则有冲突时，给出推荐方案及影响范围。
```

## 交付成熟度的含义

“给开发的文字”并不等于替现有系统拍板。主流程、权限、唯一性或平台回执有缺口时，Skill 会输出可供研发评审的具体方案，并标明哪些部分尚不能定案。

这个区分用于减少返工，不能为了显得完整就捏造接口、错误码、身份关系或业务结果。
